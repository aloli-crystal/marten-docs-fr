Les migrations garantissent que toute modification apportée aux définitions de modèles est appliquée au niveau de la base de données. Le mécanisme de migrations de Marten est conçu pour être essentiellement automatique : les migrations sont générées à partir de vos définitions de modèles lorsque vous exécutez une commande dédiée, après avoir introduit des modifications dans vos définitions de modèles.

## Vue d'ensemble

Marten est capable de créer automatiquement des migrations lorsque vous introduisez des modifications dans vos modèles.

Par exemple, supposons que vous venez d'ajouter un field string `hometown` à un modèle `Author` existant :

```crystal
class Author < Marten::Model
  field :id, :big_int, primary_key: true, auto: true
  field :first_name, :string, max_size: 255
  field :last_name, :string, max_size: 255
  // highlight-next-line
  field :hometown, :string, max_size: 255, blank: true, null: true
end
```

Après avoir introduit cette modification, vous pouvez exécuter la commande de gestion `genmigrations` comme suit :

```shell
$ marten genmigrations
Generating migrations for app 'blog':
  › Creating [src/blog/migrations/202206221856241_add_hometown_to_blog_author_table.cr]... DONE
      ○ Add hometown to blog_author table
```

Lors de l'exécution de cette commande, la définition de table correspondant à votre modèle actuel sera analysée et comparée à la table équivalente définie par vos fichiers de migration. Selon le résultat de cette analyse, un nouvel ensemble de fichiers de migration sera généré afin de prendre en compte les modifications apportées aux modèles.

Les migrations générées sont enregistrées dans un dossier `migrations` qui se trouve dans la structure locale de chaque [application](../development/applications.md). En règle générale, vous devriez toujours vérifier ce qui est réellement généré par la commande `genmigrations`. En effet, les capacités d'introspection de cette commande pourraient être limitées selon ce que vous essayez d'accomplir.

Dans l'exemple ci-dessus, le fichier de migration généré ressemble à ceci :

```crystal
# Generated by Marten 0.1.0 on 2022-06-22 18:56:24 -04:00

class Migration::Blog::V202206221856241 < Marten::Migration
  depends_on :blog, "202205290942181_previous_migration_name"

  def plan
    add_column :blog_author, :hometown, :string, max_size: 255, null: true
  end
end
```

Comme vous le voyez, la migration dépend explicitement de la migration précédente pour l'application considérée (`blog` dans ce cas) et elle définit un "plan" de migration qui implique l'ajout d'une colonne string `hometown` à la table `blog_author`.

Nous pouvons ensuite appliquer cette migration à la base de données en exécutant la commande Marten `migrate` :

```shell
$ marten migrate
Running migrations:
  › Applying blog_202206221856241_add_hometown_to_blog_author_table... DONE
```

## Commandes disponibles

Marten fournit un ensemble de quatre commandes permettant d'interagir avec les migrations de modèles :

* [`genmigrations`](../development/reference/management-commands.md#genmigrations) permet de générer des fichiers de migration en recherchant les modifications dans vos définitions de modèles
* [`migrate`](../development/reference/management-commands.md#migrate) permet d'appliquer (ou d'annuler) des migrations sur vos bases de données
* [`listmigrations`](../development/reference/management-commands.md#listmigrations) permet de lister toutes les migrations pour toutes vos [applications installées](../development/applications.md), et si elles ont déjà été appliquées ou non
* [`resetmigrations`](../development/reference/management-commands.md#resetmigrations) permet de réinitialiser plusieurs migrations en une seule

## Spécificités des connexions DB

Les migrations peuvent être utilisées avec tous les backends de base de données intégrés fournis par Marten : PostgreSQL, MySQL et SQLite. Cela dit, il existe quelques différences clés entre ces backends dont vous devriez être conscient en ce qui concerne les migrations. Ces différences proviennent du fait que toutes ces bases de données ne supportent pas les opérations d'altération de schéma ou les transactions DDL (Data Definition Language).

PostgreSQL et SQLite supportent les transactions DDL, mais MySQL ne les supporte *pas*. Ainsi, si une migration échoue lors de son application à une base de données MySQL, vous pourriez devoir annuler manuellement certaines opérations pour réessayer.

Enfin, il est à noter que SQLite ne supporte pas la plupart des opérations d'altération de schéma. Pour cette raison, Marten effectuera l'ensemble d'opérations suivant lors de l'application de modifications de modèles à une base de données SQLite :

1. créer une nouvelle table correspondant à la nouvelle définition de modèle
2. copier les données de l'ancienne table vers la nouvelle
3. supprimer l'ancienne table
4. renommer la nouvelle pour qu'elle corresponde au nom de table du modèle

## Fichiers de migration

Comme présenté dans la section [vue d'ensemble](#vue-densemble) ci-dessus, les fichiers de migration sont automatiquement générés par Marten en identifiant les modifications dans vos définitions de modèles (bien que les migrations puissent être créées et définies manuellement si nécessaire). Ces fichiers sont persistés dans un dossier `migrations` à l'intérieur du répertoire principal de chaque application.

Les migrations héritent toujours de la classe de base [`Marten::Migration`](pathname:///api/dev/Marten/DB/Migration.html). Une migration basique ressemblera à ceci :

```crystal
# Generated by Marten 0.1.0 on 2022-03-13 16:08:37 -04:00

class Migration::Main::V202203131608371 < Marten::Migration
  depends_on :users, "202203131607261_create_users_user_table"
  depends_on :main, "202203131604261_add_content_to_main_article_table"

  def plan
    add_column :main_article, :author_id, :reference, to_table: :users_user, to_column: :id, null: true
  end
end
```

Chaque migration doit définir les informations obligatoires suivantes : les **dépendances** de la migration et les **opérations** de la migration.

### Dépendances

Les migrations Marten peuvent dépendre les unes des autres. Ainsi, chaque migration définit généralement une ou plusieurs dépendances via l'utilisation de la méthode de classe [`#depends_on`](pathname:///api/dev/Marten/DB/Migration.html#depends_on(app_name%3AString|Symbol%2Cmigration_name%3AString|Symbol)-class-method), qui prend un label d'application et un nom de migration comme arguments positionnels.

Les dépendances de migration sont utilisées pour s'assurer que les modifications d'une base de données sont appliquées dans le bon ordre. Par exemple, la migration précédente fait partie de l'application `main` et dépend de deux autres migrations : premièrement, elle dépend de la migration précédente de l'application `main` (`202203131604261_add_content_to_main_article_table`). Deuxièmement, elle dépend de la migration `202203131607261_create_users_user_table` de l'application `users`. Cela a du sens étant donné que la seule opération de la migration est d'ajouter une clé étrangère `author_id` ciblant la table `users_user` à la table `main_article` : la dépendance indique à Marten d'appliquer d'abord la migration `202203131607261_create_users_user_table` (qui crée la table `users_user`) avant d'appliquer la migration ajoutant la nouvelle clé étrangère (puisque cette clé étrangère nécessite que la table ciblée existe d'abord pour être créée correctement).

Encore une fois, les dépendances de migration sont automatiquement identifiées et générées par Marten lorsque vous créez des migrations via l'utilisation de la commande [`genmigrations`](../development/reference/management-commands.md#genmigrations). Ces dépendances sont identifiées en examinant les relations DB entre l'application pour laquelle les migrations sont générées et les autres applications installées.

### Opérations

Les migrations doivent définir des opérations à appliquer (ou annuler) au niveau de la base de données. Sauf indication contraire, ces opérations sont toutes exécutées au sein d'une seule transaction pour les backends qui supportent les transactions DDL (PostgreSQL et SQLite).

Lorsqu'elles sont générées automatiquement, les migrations définiront un ensemble d'opérations à exécuter dans le cadre d'une méthode `#plan`. Cette méthode peut définir une ou plusieurs opérations. Par exemple :

```crystal
# Generated by Marten 0.1.0 on 2022-03-30 22:13:06 -04:00

class Migration::Press::V202203302213061 < Marten::Migration
  depends_on :press, "202203111822091_initial"

  def plan
    add_column :press_article, :rating, :int, null: true
    remove_column :press_article, :old_status
  end
end
```

Les migrations peuvent être *appliquées* et *annulées*. Cela signifie que lorsqu'une migration est appliquée, toutes les opérations définies dans la méthode `#plan` seront exécutées dans l'ordre où elles ont été définies. Mais si la migration est annulée, la même opération sera "inversée" dans l'ordre inverse.

Dans l'exemple précédent, le "plan" de la migration implique deux opérations : premièrement, nous ajoutons une nouvelle colonne `rating` à la table `press_article`, puis nous supprimons une colonne `old_status` de la même table. Si nous appliquions cette migration, ces deux opérations seraient exécutées dans cet ordre. Mais si nous annulions la migration, cela signifierait que nous recréerions d'abord la colonne `old_status` dans la table `press_article`, puis nous supprimerions la colonne `rating` de la table `press_article`.

L'aspect bidirectionnel de la méthode `#plan` peut être exploité pour la plupart des cas d'utilisation de migration, mais il pourrait y avoir des situations où les opérations impliquées lors de l'*application* de la migration diffèrent de celles impliquées lors de l'*annulation* de la migration. Dans ces situations, les opérations d'application peuvent être définies dans une méthode `#forward` tandis que les opérations d'annulation peuvent être définies dans une méthode `#backward` :

```crystal
# Generated by Marten 0.1.0 on 2022-03-30 22:13:06 -04:00

class Migration::Press::V202203302213061 < Marten::Migration
  depends_on :press, "202203111822091_initial"

  def forward
    add_column :press_article, :rating, :int, null: true
    remove_column :press_article, :old_status
  end

  def backward
    # do something else
  end
end
```

## Générer des migrations

La génération de migrations est possible via l'utilisation de la commande de gestion [`genmigrations`](../development/reference/management-commands.md#genmigrations). Cette commande analysera la définition de table correspondant à vos modèles actuels et la comparera à la table équivalente définie par vos fichiers de migration. En fonction du résultat de cette analyse, un nouvel ensemble de migrations sera créé et persisté dans les dossiers `migrations` de vos applications.

:::info
La commande `genmigrations` ne peut créer des migrations que pour les [applications installées](../development/applications.md). Si la commande ne détecte pas les modifications prévues, assurez-vous que vos modèles font partie d'une application installée.
:::

L'exécution de `marten genmigrations` générera des migrations pour *tous* les modèles fournis par vos applications installées, mais il est possible de restreindre la génération à un label d'application spécifique en spécifiant un argument supplémentaire comme suit :

```shell
$ marten genmigrations my_app
```

Une autre option de commande utile est `--empty`, qui permet de générer un fichier de migration vide (sans opérations définies) :

```shell
$ marten genmigrations my_app --empty
```

## Appliquer et annuler des migrations

Comme mentionné précédemment, les migrations peuvent être appliquées en exécutant la commande de gestion [`migrate`](../development/reference/management-commands.md#migrate).

L'exécution de `marten migrate` exécutera les migrations non appliquées pour vos applications installées. Cela dit, il est possible de s'assurer que seules les migrations d'une application spécifique sont appliquées en spécifiant un argument supplémentaire comme suit :

```shell
$ marten migrate my_app
```

Pour annuler certaines migrations (ou n'en appliquer que certaines jusqu'à une version donnée), il est possible de spécifier un autre argument correspondant à la version d'une migration ciblée. Par exemple, nous pourrions annuler toutes les migrations après la version `202203111821451` pour l'application `my_app` en exécutant :

```shell
$ marten migrate my_app 202203111821451
```

Si vous souhaitez annuler toutes les migrations d'une application spécifique, vous pouvez le faire en ciblant la version `zero` :

```shell
$ marten migrate my_app zero
```

Enfin, il est à noter qu'il est possible de "simuler" le fait que des migrations sont appliquées ou annulées en utilisant l'option de commande `--fake`. En faisant cela, seul le fait que la migration a été appliquée (ou annulée) sera enregistré, et aucune opération de migration ne sera exécutée :

```shell
$ marten migrate my_app 202203111821451 --fake
```

## Transactions

Les opérations d'une migration seront exécutées à l'intérieur d'une seule transaction par défaut, sauf si cette fonctionnalité n'est pas supportée par le backend de base de données (ce qui est le cas pour MySQL).

Il est possible de désactiver ce comportement par défaut en utilisant la méthode [`#atomic`](pathname:///api/dev/Marten/DB/Migration.html#atomic(atomic%3ABool)-class-method), dans la classe de migration :

```crystal
# Generated by Marten 0.1.0 on 2022-03-30 22:13:06 -04:00

class Migration::Press::V202203302213061 < Marten::Migration
  depends_on :press, "202203111822091_initial"

  atomic false

  def plan
    add_column :press_article, :rating, :int, null: true
    remove_column :press_article, :old_status
  end
end
```

## Migrations de données

Parfois, il est nécessaire d'écrire des migrations qui ne modifient pas le schéma de la base de données mais qui écrivent effectivement des données dans la base de données. C'est souvent le cas lors du remplissage rétroactif de valeurs de colonnes par exemple. Pour ce faire, Marten offre la possibilité d'exécuter du code arbitraire dans le cadre de migrations via l'utilisation d'une opération spéciale `#run_code`.

Par exemple, la migration suivante exécutera la méthode `#run_forward_code` lors de l'application de la migration, et elle exécutera la méthode `#run_backward_code` lors de l'annulation :

```crystal
# Generated by Marten 0.1.0 on 2022-03-30 22:13:06 -04:00

class Migration::Press::V202203302213061 < Marten::Migration
  depends_on :press, "202203111822091_initial"

  def plan
    run_code :run_forward_code, :run_backward_code
  end

  def run_forward_code
    # do something
  end

  def run_backward_code
    # do something
  end
end
```

`#run_code` peut être appelé avec un seul argument si vous ne souhaitez pas spécifier de méthode "backward". La migration suivante est techniquement équivalente à celle de l'exemple précédent :

```crystal
# Generated by Marten 0.1.0 on 2022-03-30 22:13:06 -04:00

class Migration::Press::V202203302213061 < Marten::Migration
  depends_on :press, "202203111822091_initial"

  def forward
    run_code :run_forward_code
  end

  def backward
    run_code :run_backward_code
  end

  def run_forward_code
    # do something
  end

  def run_backward_code
    # do something
  end
end
```

:::info
Les logiques de migration de données ne peuvent pas être définies directement dans les méthodes `#forward` et `#backward`. En effet, les méthodes `#plan`, `#forward` et `#backward` ne font rien à la base de données directement : elles construisent simplement un plan d'opérations que Marten utilisera lors de l'application ou de l'annulation des migrations. C'est pourquoi il est nécessaire d'utiliser l'opération `#run_code` lors de la définition de migrations de données.
:::

Il est à noter qu'un moyen pratique de commencer à écrire une migration de données est de générer un squelette de migration vide pour l'application ciblée :

```shell
$ marten genmigrations my_app --empty
```

## Exécuter des instructions SQL personnalisées

Parfois, les opérations de migration intégrées fournies par Marten peuvent ne pas suffire et vous pourriez vouloir exécuter des instructions SQL arbitraires sur la base de données dans le cadre de migrations.

Pour ce faire, vous pouvez utiliser l'opération de migration [`#execute`](./reference/migration-operations.md#execute). Cette opération doit être appelée avec une chaîne d'instruction d'application comme premier argument positionnel, et elle peut également prendre un second argument positionnel (et optionnel) afin de spécifier l'instruction à exécuter lors de l'annulation de la migration (ce qui n'est utile que lors de la définition d'une opération bidirectionnelle dans la méthode `#plan`).

Par exemple :

```crystal
# Generated by Marten 0.1.0 on 2022-03-30 22:13:06 -04:00

class Migration::Press::V202203302213061 < Marten::Migration
  depends_on :press, "202203111822091_initial"

  def plan
    execute("CREATE EXTENSION 'uuid-ossp';")
  end
end
```

## Réinitialiser les migrations

Lorsque votre application commence à avoir un certain nombre de migrations, il peut devenir intéressant de les réinitialiser. Cela signifie réduire toutes les migrations existantes à un seul fichier de migration. Ceci peut être réalisé via l'utilisation de la commande de gestion [`resetmigrations`](../development/reference/management-commands.md#resetmigrations).

Par exemple, considérons la situation suivante où nous avons trois migrations sous l'application `my_app` :

```shell
$ marten listmigrations
[my_app]
  [✔] my_app_202203111821451_create_my_app_article_table
  [✔] my_app_202203111822091_add_status_to_my_app_article_table
  [✔] my_app_202204051755101_add_rating_to_my_app_article_table
```

L'exécution de la commande `resetmigrations` produira la sortie suivante :

```shell
$ marten resetmigrations my_app
Generating migrations for app 'my_app':
  › Creating [src/my_app/migrations/202206261646061_auto.cr]... DONE
      ○ Create my_app_article table
```

Si nous examinons la migration générée, vous remarquerez qu'elle inclut plusieurs appels à la méthode de classe [`#replaces`](pathname:///api/dev/Marten/DB/Migration.html#replaces(app_name%3AString|Symbol%2Cmigration_name%3AString|Symbol)-class-method) :

```crystal
# Generated by Marten 0.1.0 on 2022-06-26 16:46:06 -04:00

class Migration::MyApp::V202206261646061 < Marten::Migration
  replaces :my_app, "202203111821451_create_my_app_article_table"
  replaces :my_app, "202203111822091_add_status_to_my_app_article_table"
  replaces :my_app, "202204051755101_add_rating_to_my_app_article_table"

  def plan
    create_table :my_app_article do
      column :id, :big_int, primary_key: true, auto: true
      column :title, :string, max_size: 155
      column :body, :text
      column :status, :string, max_size: 64, null: true
      column :rating, :int, null: true
    end
  end
end
```

Ces appels à la méthode `#replaces` indiquent les migrations précédentes que la migration actuelle remplace. Cette nouvelle migration peut être commitée dans le dépôt de votre projet. Elle peut ensuite être appliquée comme n'importe quelle autre migration (même si la base de données sous-jacente était déjà à jour avec les dernières migrations). Les migrations suivantes l'utiliseront comme dépendance et ignoreront toutes les migrations qui ont été remplacées.

Plus tard, vous pouvez décider de supprimer les anciennes migrations (celles qui ont été remplacées par la nouvelle migration). Mais évidemment, vous ne devriez le faire qu'après un certain temps afin de donner aux développeurs la chance d'appliquer toutes les dernières migrations.

:::warning
La commande de gestion `resetmigrations` ne reportera pas les opérations `run_code` ni aucune autre opération ajoutée "manuellement". En fait, `resetmigrations` examinera simplement vos définitions de modèles et essaiera de recréer un nouveau fichier de migration depuis le début (sans considérer vos anciens fichiers de migration). Ainsi, si votre base de données nécessite des opérations spéciales `run_code` ou `run_sql`, vous devriez vous assurer que celles-ci sont ajoutées en tant que migrations suivantes.
:::
