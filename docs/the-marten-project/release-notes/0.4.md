_13 janvier 2024._

## Prérequis et compatibilité

Crystal 1.9, 1.10 et 1.11.

## Nouvelles fonctionnalités

### Générateurs

Marten fournit désormais un mécanisme de générateurs qui facilite la création de diverses abstractions, fichiers et structures au sein d'un projet existant. Cette fonctionnalité est disponible via la commande de gestion [`gen`](../../development/reference/management-commands.md#gen) et facilite la génération de composants clés tels que les [modèles](../../models-and-databases/introduction.md), les [schemas](../../schemas/introduction.md), les [emails](../../emailing/introduction.md) ou les [applications](../../development/applications.md). L'[application d'authentification](../../authentication/introduction.md) peut désormais également être ajoutée facilement à des projets existants grâce aux générateurs. En utilisant les générateurs, les développeurs peuvent améliorer leur flux de travail et accélérer le développement de leurs projets Marten tout en suivant les bonnes pratiques.

Voici quelques exemples illustrant l'utilisation de la commande de gestion [`gen`](../../development/reference/management-commands.md#gen) :

```sh
# Generate a model in the admin app:
marten gen model User name:string email:string --app admin

# Generate a new TestEmail email in the blog application:
marten gen email TestEmail --app blog

# Add a new 'blogging' application to the current project:
marten gen app blogging

# Add the authentication application to the current project:
margen gen auth
```

Vous pouvez en savoir plus sur le mécanisme de générateurs dans la [documentation dédiée](../../development/generators.md). Tous les générateurs disponibles sont également listés dans la [référence des générateurs](../../development/reference/generators.md).

### Héritage multi-table

Il est désormais possible de définir des modèles qui héritent d'autres modèles concrets (c.-à-d. des modèles non abstraits). Dans cette situation, chaque modèle peut être utilisé/interrogé individuellement et possède sa propre table de base de données associée. Le framework définit automatiquement un ensemble de "liens" entre chaque modèle qui utilise l'héritage multi-table et ses modèles parents afin de garantir que la structure relationnelle et la hiérarchie d'héritage sont maintenues.

Par exemple :

```crystal
class Person < Marten::Model
  field :id, :big_int, primary_key: true, auto: true
  field :first_name, :string, max_size: 100
  field :last_name, :string, max_size: 100
end

class Employee < Person
  field :company_name, :string, max_size: 100
end

employee = Employee.filter(first_name: "John").first!
employee.first_name # => "John"
```

Tous les champs définis dans le modèle `Person` sont accessibles lors de l'interaction avec les enregistrements du modèle `Employee` (malgré le fait que les données elles-mêmes sont stockées dans des tables distinctes).

Vous pouvez en savoir plus sur ce nouveau type d'héritage de modèle dans [Héritage multi-table](../../models-and-databases/introduction.md#multi-table-inheritance).

### Callbacks de handler de schema

Les handlers qui héritent du handler de schema de base - [`Marten::Handlers::Schema`](pathname:///api/0.4/Marten/Handlers/Schema.html) - ou de l'une de ses sous-classes (comme [`Marten::Handlers::RecordCreate`](pathname:///api/0.4/Marten/Handlers/RecordCreate.html) ou [`Marten::Handlers::RecordUpdate`](pathname:///api/0.4/Marten/Handlers/RecordUpdate.html)) peuvent désormais définir de nouveaux types de callbacks qui permettent de manipuler facilement l'instance de [schema](../../schemas/introduction.md) considérée et de définir la logique à exécuter avant la validation du schema ou après (par ex. lorsque la validation du schema réussit ou échoue) :

* [`before_schema_validation`](../../handlers-and-http/callbacks.md#before_schema_validation)
* [`after_schema_validation`](../../handlers-and-http/callbacks.md#after_schema_validation)
* [`after_successful_schema_validation`](../../handlers-and-http/callbacks.md#after_successful_schema_validation)
* [`after_failed_schema_validation`](../../handlers-and-http/callbacks.md#after_failed_schema_validation)

Par exemple, le callback [`after_successful_schema_validation`](../../handlers-and-http/callbacks.md#after_successful_schema_validation) peut être utilisé pour créer un message flash après qu'un schema a été validé avec succès :

```crystal
class ArticleCreateHandler < Marten::Handlers::Schema
  success_route_name "home"
  template_name "articles/create.html"
  schema ArticleSchema

  after_successful_schema_validation :generate_success_flash_message

  private def generate_success_flash_message : Nil
    flash[:notice] = "Article successfully created!"
  end
end
```

Consultez [Callbacks de handler de schema](../../handlers-and-http/callbacks.md#schema-handler-callbacks) pour en savoir plus sur ces nouveaux types de callbacks.

### Champ URL pour les modèles et les schemas

Il est désormais possible de définir des champs `url` dans les [modèles](../../models-and-databases/reference/fields.md#url) et les [schemas](../../schemas/reference/fields.md#url). Ceux-ci vous permettent de persister facilement des URL valides dans vos modèles mais aussi d'attendre des valeurs URL valides dans les données validées via l'utilisation de schemas.

Par exemple :

```crystal
class User < Marten::Model
  field :id, :big_int, primary_key: true, auto: true
  field :website_url, :url, blank: true, null: true
end
```

### Champ slug pour les modèles et les schemas

Il est désormais possible de définir des champs `slug` dans les [modèles](../../models-and-databases/reference/fields.md#slug) et les [schemas](../../schemas/reference/fields.md#slug). Ceux-ci vous permettent de persister facilement des valeurs slug valides (c.-à-d. des chaînes qui ne peuvent contenir que des caractères, des chiffres, des tirets et des underscores) dans vos modèles mais aussi d'attendre de telles valeurs dans les données validées via l'utilisation de schemas.

Par exemple :

```crystal
class User < Marten::Model
  field :id, :big_int, primary_key: true, auto: true
  field :username, :slug
end
```

### Fonctionnalités mineures

#### Modèles et bases de données

* La prise en charge de la suppression d'enregistrements des champs many-to-many a été ajoutée et les query sets de champs many-to-many fournissent désormais une méthode d'aide [`#remove`](pathname:///api/0.4/Marten/DB/Query/ManyToManySet.html#remove(*objs%3AM)%3ANil-instance-method) permettant de supprimer facilement des enregistrements spécifiques d'une relation donnée. Vous pouvez en savoir plus sur cette capacité dans [Relations many-to-many](../../models-and-databases/relationships.md#many-to-many-relationships).
* La prise en charge de la suppression de toutes les références aux enregistrements ciblés par les champs many-to-many a été ajoutée. En effet, les query sets de champs many-to-many fournissent désormais une méthode [`#clear`](pathname:///api/0.4/Marten/DB/Query/ManyToManySet.html#clear%3ANil-instance-method) permettant de vider facilement une relation spécifique. Vous pouvez en savoir plus sur cette capacité dans [Relations many-to-many](../../models-and-databases/relationships.md#many-to-many-relationships).
* Il est désormais possible de spécifier des tableaux d'enregistrements à ajouter ou supprimer d'un query set de relation many-to-many, via l'utilisation des méthodes [`#add`](pathname:///api/0.4/Marten/DB/Query/ManyToManySet.html#add(*objs%3AM)-instance-method) et [`#remove`](pathname:///api/0.4/Marten/DB/Query/ManyToManySet.html#remove(*objs%3AM)%3ANil-instance-method). Consultez la [documentation associée](../../models-and-databases/relationships.md#interacting-with-related-records-2) pour en savoir plus sur l'interaction avec les enregistrements ciblés par les relations many-to-many.
* Les enregistrements ciblés par les relations inverses qui sont contribuées aux modèles par [`one_to_one`](../../models-and-databases/reference/fields.md#one_to_one) (c.-à-d. lors de l'utilisation de l'option [`related`](../../models-and-databases/reference/fields.md#related-2)) sont désormais mémorisés lorsque les méthodes correspondantes sont appelées sur les instances de modèle liées.
* Les champs de relation qui contribuent des méthodes retournant des query sets aux modèles (comme les champs [`many_to_one`](../../models-and-databases/reference/fields.md#many_to_one) ou [`many_to_many`](../../models-and-databases/reference/fields.md#many_to_many)) s'assurent désormais que ces objets query set sont mémorisés au niveau de l'enregistrement. Les variables d'instance correspondantes sont également réinitialisées lorsque les enregistrements considérés sont rechargés. Cela permet de limiter le nombre de requêtes impliquées lors de l'itération multiple sur les enregistrements ciblés par un champ [`many_to_many`](../../models-and-databases/reference/fields.md#many_to_many) par exemple.
* La méthode de query set [`#order`](../../models-and-databases/reference/query-set.md#order) peut désormais être appelée directement sur les classes de modèle pour permettre de récupérer tous les enregistrements du modèle considéré dans un ordre spécifique.
* Une méthode de modèle [`#pk?`](pathname:///api/0.4/Marten/DB/Model/Table.html#pk%3F%3ABool-instance-method) peut désormais être utilisée pour déterminer si une valeur de clé primaire est définie sur un enregistrement de modèle donné.
* La méthode de query set [`#join`](../../models-and-databases/reference/query-set.md#join) permet désormais de pré-sélectionner les relations inverses one-to-one. Cela permet essentiellement de remonter un champ [`one_to_one`](../../models-and-databases/reference/fields.md#one_to_one) jusqu'à l'enregistrement de modèle sur lequel le champ est spécifié.
* La méthode de query set [`#count`](../../models-and-databases/reference/query-set.md#count) peut désormais prendre un nom de champ optionnel pour compter le nombre d'enregistrements qui ont une valeur non nulle pour la colonne correspondante dans la base de données.

#### Handlers et HTTP

* Il est désormais optionnel de définir un nom pour les maps de routes incluses (mais définir un nom pour les routes individuelles associées aux [handlers](../../handlers-and-http/introduction.md) reste obligatoire). Vous pouvez en savoir plus à ce sujet dans [Définir des routes incluses](../../handlers-and-http/routing.md#defining-included-routes).
* Le handler générique [`Marten::Handlers::Schema`](pathname:///api/0.4/Marten/Handlers/Schema.html) permet désormais de modifier le nom de contexte de l'objet schema grâce à l'utilisation de la méthode [`#schema_context_name`](pathname:///api/0.4/Marten/Handlers/Schema.html#schema_context_name(name%3AString|Symbol)-class-method).
* Il est désormais possible de spécifier des codes de statut symboliques lors de l'utilisation des méthodes d'aide de réponse [`#respond`](../../handlers-and-http/introduction.md#respond), [`#render`](../../handlers-and-http/introduction.md#render), [`#head`](../../handlers-and-http/introduction.md#head) et [`#json`](../../handlers-and-http/introduction.md#json). Ces symboles doivent être conformes aux valeurs de l'enum [`HTTP::Status`](https://crystal-lang.org/api/HTTP/Status.html).
* Le hash des paramètres de routage correspondants disponible depuis les handlers via la méthode `#params` peut accepter des symboles et des chaînes lors des recherches par clé.
* Le [middleware GZip](../../handlers-and-http/reference/middlewares.md#gzip-middleware) intègre désormais une stratégie d'atténuation contre l'attaque BREACH. Cette stratégie (décrite dans le [papier Heal The Breach](https://ieeexplore.ieee.org/document/9754554)) consiste à introduire jusqu'à 100 octets aléatoires dans les réponses GZip pour renforcer la sécurité contre de telles attaques.
* Un nouveau type de callback [`before_render`](../../handlers-and-http/callbacks.md#before_render) est désormais disponible pour les handlers. Ces callbacks sont exécutés avant le rendu d'un [template](../../templates/introduction.md) afin de produire une réponse. En tant que tels, ils sont bien adaptés pour ajouter de nouvelles variables au contexte global du template afin qu'elles soient disponibles au moment de l'exécution du template.
* Tous les handlers ont désormais accès à un [contexte de template global](../../handlers-and-http/introduction.md#global-template-context) via la méthode [`#context`](pathname:///api/0.4/Marten/Handlers/Base.html#context-instance-method). Cet objet de contexte de template est disponible pendant toute la durée de vie du handler considéré et peut être muté pour définir quelles variables sont mises à disposition du moteur de template lors du rendu des templates (soit via l'utilisation de la méthode d'aide [`#render`](../../handlers-and-http/introduction.md#render) ou lors du rendu de templates dans le cadre de sous-classes du handler générique [`Marten::Handlers::Template`](../../handlers-and-http/generic-handlers.md#rendering-a-template)). Cette fonctionnalité peut être combinée avec le callback [`before_render`](../../handlers-and-http/callbacks.md#before_render) pour introduire sans effort de nouvelles variables dans le contexte utilisé pour le rendu d'un template et la génération d'une réponse de handler.

#### Templates

* Un tag de template [`with`](../../templates/reference/tags.md#with) a été introduit pour faciliter l'assignation d'une ou plusieurs variables à l'intérieur d'un bloc de template.
* Un tag de template [`time`](../../templates/reference/filters.md#time) a été introduit pour permettre de produire la représentation en chaîne d'une variable de temps selon un [format de temps](https://crystal-lang.org/api/Time/Format.html) spécifique.
* Un tag de template [`escape`](../../templates/reference/filters.md#escape) a été introduit pour faciliter l'échappement explicite des [chaînes sûres](../../templates/introduction.md#auto-escaping) dans les templates.
* La possibilité de configurer le traitement des variables indéfinies/inconnues a été ajoutée au framework : par défaut, ces variables sont traitées comme des valeurs `nil` (donc rien n'est affiché pour ces variables, et elles sont évaluées comme falsey dans les conditions if). Ce comportement peut être configuré via le paramètre [`templates.strict_variables`](../../development/reference/settings.md#strict_variables), et vous pouvez en savoir plus à ce sujet dans [Variables strictes](../../templates/introduction.md#strict-variables).

#### Développement

* La commande de gestion [`new`](../../development/reference/management-commands.md#new) accepte désormais une option optionnelle `--database` qui peut être utilisée pour préconfigurer la base de données de l'application (par ex. `--database=postgresql`).
* Une commande de gestion [`clearsessions`](../../development/reference/management-commands.md#clearsessions) a été introduite afin de faciliter le processus de nettoyage des entrées de session expirées.
* Les commandes de gestion personnalisées peuvent désormais définir comment elles souhaitent gérer les arguments inconnus ou indéfinis grâce à l'utilisation de la méthode [`#on_unknown_argument`](pathname:///api/0.4/Marten/CLI/Manage/Command/Base.html#on_unknown_argument(%26block%3AString->)-instance-method). Cela peut être utilisé pour implémenter des commandes de gestion qui peuvent accepter un nombre variable d'arguments positionnels.
* Les commandes de gestion personnalisées peuvent désormais définir comment elles souhaitent gérer les options invalides grâce à l'utilisation de la méthode [`#on_invalid_option`](pathname:///api/0.4/Marten/CLI/Manage/Command/Base.html#on_invalid_option(%26block%3AString->)-instance-method).

#### Envoi d'emails

* Les [emails](../../emailing/introduction.md) fournissent désormais un ensemble de [callbacks](../../emailing/callbacks.md) qui facilitent la définition de logique déclenchée à différentes étapes du cycle de vie d'un email (avant/après la livraison d'un email, avant le rendu du template de l'email).

#### Authentification

* L'application d'authentification générée propose désormais la possibilité de modifier le mot de passe de l'utilisateur actuellement connecté.

## Changements rétro-incompatibles

### Handlers et HTTP

* Les [stores de session](../../handlers-and-http/sessions.md#session-stores) personnalisés doivent désormais implémenter une méthode [`#clear_expired_entries`](pathname:///api/0.4/Marten/HTTP/Session/Store/Base.html#clear_expired_entries%3ANil-instance-method) (permettant de nettoyer les entrées de session expirées si cela est applicable pour le store considéré).
* L'introduction du [contexte de template global](../../handlers-and-http/introduction.md#global-template-context) implique que les handlers génériques qui surchargaient la méthode `#context` (afin d'insérer des objets d'enregistrement ou de schema dans le contexte du template par exemple) utilisent désormais des callbacks [`before_render`](../../handlers-and-http/callbacks.md#before_render) afin de muter le contexte global et définir les mêmes variables. Les sous-classes de handlers génériques qui surchargaient cette méthode `#context` et appelaient `super` dedans devront probablement être mises à jour pour utiliser le callback [`before_render`](../../handlers-and-http/callbacks.md#before_render) afin d'ajouter des variables personnalisées au [contexte de template global](../../handlers-and-http/introduction.md#global-template-context).

### Templates

* Le filtre de template [`default`](../../templates/reference/filters.md#default) retournera désormais la valeur par défaut spécifiée si la valeur entrante est falsey ou vide.

### Envoi d'emails

* L'introduction du [contexte de template global](../../emailing/introduction.md#modifying-the-template-context) implique que les emails qui définissaient explicitement une méthode `#context` (par ex. pour définir un hash de variables de template à partir de variables d'instance locales) ne fonctionneront plus. À la place, ces emails doivent désormais utiliser le callback [`before_render`](../../emailing/callbacks.md#before_render) afin d'[ajouter ces variables à l'objet de contexte de template de l'email](../../emailing/introduction.md#modifying-the-template-context).
